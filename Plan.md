# План проверки и автоматизации приложения «Мобильный хоспис»

## 1. Границы тестирования и реализованный функционал

### 1.1. Границы тестирования (что входит в проверку)
- **Объект тестирования:** мобильное приложение «Мобильный хоспис» (Android).
- **Платформа:** эмулятор Android с API 36 (целевая версия по заданию).
- **Область тестирования:** только клиентская часть (UI/UX, функциональность, навигация, жизненный цикл, прерывания, совместимость, инструменты). Бэкенд-логика, API, базы данных не тестируются.
- **Не тестируется:** работа на реальных устройствах (только эмулятор), поведение при отсутствии интернета, масштабирование, нагрузочное тестирование.

### 1.2. Реализованный функционал (модули приложения)
На основе изучения приложения выделены следующие модули:

1. **Авторизация**
   - Вход с логином/паролем (валидные/невалидные данные)
   - Выход из учётной записи
   - Валидация полей

2. **Новости (отображение и управление)**
   - Отображение списка новостей на экранах Main и News
   - Панель управления (Control panel) — открытие, просмотр полного списка
   - Создание новости (форма с полями: Category, Title, Publication date, Time, Description, Active)
   - Редактирование новости (изменение полей, отмена)
   - Удаление новости (с подтверждением и отменой)
   - Фильтрация (по категории, статусу Active/Not active, диапазону дат через календарь)
   - Сортировка (по дате)

3. **Цитаты**
   - Открытие цитат по кнопке «бабочка»
   - Закрытие цитат

4. **Навигация**
   - Переход между Main и News
   - Использование системной кнопки «Назад»
   - Поворот экрана во время работы приложения

5. **Жизненный цикл и прерывания**
   - Сворачивание и разворачивание приложения
   - Длительное нахождение в фоне (5 минут)
   - Блокировка экрана во время работы приложения
   - Входящий звонок, системные уведомления

6. **Совместимость**
   - Работа на целевой версии Android (API 36)
   - Поведение в режиме экономии энергии

7. **Инструменты**
   - Мониторинг памяти через профайлер Android Studio
   - Ручной стресс-тест (быстрые переходы между экранами)

### 1.3. Основа для тестов
На основе выделенного функционала составлен чек-лист (36 проверок) и детальные тест-кейсы (35 штук), покрывающие все модули, включая позитивные и негативные сценарии, UI/UX, стабильность и работу с инструментами.

## 2. Типы тестирования

В рамках проекта применяются следующие виды тестирования:

| № | Тип тестирования | Что проверяется |
|---|------------------|-----------------|
| 1 | **Функциональное тестирование** | Проверка корректности работы всех заявленных функций: авторизация, создание/редактирование/удаление новостей, фильтрация, сортировка, открытие/закрытие цитат, навигация. Проверяются как позитивные, так и негативные сценарии (неверные данные, пустые поля, ошибки фильтрации). |
| 2 | **UI-тестирование (графический интерфейс)** | Проверка визуального соответствия: отображение всех элементов (кнопки, поля, списки, сообщения), адаптация к повороту экрана (если поддерживается), читаемость текста, размер и кликабельность элементов, корректное отображение состояний (пустой список, ошибки). |
| 3 | **Тестирование навигации** | Проверка переходов между экранами (Main ↔ News, открытие панели управления, открытие форм создания/редактирования, возврат через системную кнопку «Назад»). Убеждаемся, что навигация интуитивна и не приводит к потере данных. |
| 4 | **Тестирование жизненного цикла** | Проверка поведения приложения при сворачивании (кнопка «Домой») и последующем разворачивании, при блокировке экрана, а также при длительном нахождении в фоне (5 минут). Ожидается, что состояние приложения сохраняется (поля не сбрасываются, список не перезагружается). |
| 5 | **Тестирование прерываний** | Проверка реакции приложения на внешние события: входящий звонок, системные уведомления (например, низкий заряд батареи). Приложение должно корректно уходить в фон и восстанавливаться без потери данных и без крашей. |
| 6 | **Тестирование совместимости** | Проверка работы приложения на целевой версии ОС (Android API 36) и в режиме экономии энергии. Убеждаемся, что приложение запускается и выполняет основные сценарии без ошибок, а в режиме экономии сохраняет стабильность (допустимы незначительные замедления). |
| 7 | **Тестирование безопасности (сессия)** | Проверка, что после выхода из учётной записи данные сессии сбрасываются и доступ к приложению без повторной авторизации невозможен. |
| 8 | **Инструментальное тестирование** | Проверка отсутствия утечек памяти с помощью профайлера Android Studio, а также стабильности при быстрых переходах между экранами (ручной стресс-тест). |
| 9 | **Тестирование производительности (базовое)** | Оценка времени холодного запуска, плавности прокрутки списка, скорости открытия форм и отклика интерфейса на действия пользователя. Отсутствие утечек памяти при циклических операциях. |

## 3. План автоматизации

### 3.1. Инструменты и библиотеки
- **Язык:** Kotlin
- **Фреймворк для UI-тестов:** Espresso
- **Сборка:** Gradle
- **Отчёты:** Allure
- **Дополнительно:** ADB для логирования (при необходимости), профайлер для ручного мониторинга памяти.

### 3.2. Структура автоматизации
- Тесты будут организованы по модулям, соответствующим разделам чек-листа.
- Каждый тест будет проверять один сценарий (например, авторизацию, создание новости).
- Будут использованы Page Object (если применимо) для упрощения поддержки.

### 3.3. Настройка проекта
- Добавлены зависимости Espresso, JUnit, Allure в `build.gradle`.
- В `gradle.properties` добавлен флаг `android.injected.androidTest.leaveApksInstalledAfterRun=true` для сохранения приложения после тестов.
- Создана директория `androidTest` с тестовыми классами.

### 3.4. Написание тестов
Планируется автоматизировать следующие ключевые сценарии (в порядке приоритета):
- Авторизация (успешная, неуспешная, выход)
- Создание, редактирование, удаление новости
- Фильтрация по категории, статусу и дате
- Сортировка
- Открытие и закрытие цитат
- Навигация (переходы, кнопка «Назад»)
- Жизненный цикл (сворачивание/разворачивание, блокировка экрана)

Для каждого теста добавлены проверки (assertions) после каждого действия.

### 3.5. Отчёты
- Allure будет использован для формирования отчётов с шагами, скриншотами при падении.
- После прогона тестов будет создан архив `allure-results.zip`.
